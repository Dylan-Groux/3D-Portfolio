Le langage du navigateur

En 1995, une page web était une feuille figée. JavaScript est né pour la faire réagir sans attendre le serveur. Ce cours suit le trajet complet d'une page, ouvre le moteur qui fait tourner ton code, et explique les bizarreries que le langage traîne depuis ses dix premiers jours.

Le problème de départ

1 · Chaque vérification, un aller-retour

Avant JavaScript, le navigateur savait afficher du HTML, et c'est tout. Pour savoir si un e-mail était bien écrit, il fallait envoyer le formulaire au serveur, attendre sa réponse, puis recommencer en cas d'erreur.

Essaie les deux époques. L'e-mail de départ a un défaut : il lui manque l'arobase.

VOIR LA RÉPONSE

Non, jamais. Le JavaScript tourne sur la machine de l'utilisateur, donc l'utilisateur en a le contrôle. Il peut le désactiver, le modifier dans les outils de développement, ou envoyer la requête sans passer par la page du tout :

curl -X POST https://ton-site.fr/inscription -d "email=nimportequoi"

La vérification côté navigateur sert le confort (réponse instantanée, moins d'allers-retours). La vérification côté serveur sert la sécurité et l'intégrité des données. Dans la machine ci-dessus, en mode JavaScript, regarde la case « Qui a vérifié ? » quand l'e-mail est correct : les deux.

Les faits

2 · Dix jours, trois noms, une norme

En 1995, Netscape édite le navigateur le plus utilisé. Il embauche Brendan Eich, à l'origine pour mettre le langage Scheme dans le navigateur. La direction change de cap : il faut un petit langage de « colle », assez simple pour qu'un designer écrive quelques lignes directement dans le HTML, et dont la syntaxe ressemble à Java.

Java, lui, est vu comme le langage des composants lourds, écrit par des programmeurs professionnels. JavaScript, c'est pour tout le monde.

Le nom appartient à Oracle

La marque « JavaScript » appartenait à Sun. Oracle en a hérité en rachetant Sun. C'est pour ça que la norme officielle s'appelle toujours ECMAScript, et que les comités parlent d'ES2015, ES2025.

Ce que JavaScript manipule

4 · Le DOM : la page devient un arbre

Quand le navigateur lit le HTML, il le transforme en DOM (Document Object Model) : un arbre d'objets, un par balise. JavaScript ne modifie pas le fichier HTML. Il modifie cet arbre en mémoire, et le navigateur redessine seulement ce qui a changé.

Chaque bouton ci-dessous exécute vraiment la ligne de code affichée sur la mini-page. L'arbre de droite est relu à chaque fois.

Et React, dans tout ça ?

React fait la même chose, en automatique. Tu décris ce que la page doit afficher pour un état donné, et React calcule les modifications minimales du DOM à faire quand l'état change. Sous le capot, ce sont les mêmes append, remove et textContent.

Comment ton code s'exécute

5 · Un seul fil : la boucle d'événements

JavaScript n'exécute qu'une chose à la fois, sur une seule pile d'appels. Pour ne pas bloquer la page pendant qu'il attend un minuteur ou une réponse réseau, il confie l'attente au navigateur et met la suite dans une file. La boucle d'événements vide ces files quand la pile est libre.

Devine dans quel ordre la console affiche les lettres, puis avance pas à pas.

Ce que ça change pour toi

Une boucle de calcul très longue bloque tout : plus de clics, plus d'animation, la page « gèle ». Et le résultat d'un fetch() n'existe jamais à la ligne suivante : il arrive plus tard, par la file. C'est exactement ce que règle await.

L'héritage des dix jours

6 · Les pièges qu'on ne corrigera jamais

Écrit en dix jours, déployé sur des millions de sites : JavaScript a gardé des comportements étranges. On ne peut pas les corriger, parce que des sites existants en dépendent. La règle des comités de normalisation, c'est « ne pas casser le web » : on ajoute (let, ===, le mode strict), on ne retire rien.

Devine chaque résultat avant de l'afficher. Les résultats sont calculés en direct par ton navigateur.

MACHINE 5 · LA CONSOLE PIÉGÉE

Pourquoi typeof null vaut "object"

Dans le tout premier moteur, chaque valeur portait une petite étiquette de type dans ses bits de poids faible. L'étiquette 000 voulait dire « objet ». Or null était représenté par le pointeur zéro : ses bits de poids faible valaient donc 000 aussi. Le bug a été repéré, mais le corriger casserait du code existant.

2026

7 · De la colle de 1995 au langage partout

Aujourd'hui, JavaScript est utilisé côté navigateur par 98,9 % des sites web (W3Techs, novembre 2026). C'est le seul langage que tous les navigateurs exécutent nativement depuis le début. Il est aussi sorti du navigateur.

2008 · V8

Le moteur de Chrome compile JavaScript en code machine pendant l'exécution (compilation « juste à temps »). Ce gain de vitesse ouvre la voie aux applications web lourdes, puis à Node.js.

2009 · NODE.JS

V8 hors du navigateur : JavaScript sur un serveur, en ligne de commande, dans les outils de build. npm devient le plus gros registre de paquets.

2012 · TYPESCRIPT

Microsoft ajoute des types vérifiés avant l'exécution. TypeScript se compile en JavaScript : le navigateur ne voit jamais les types.

2013 · REACT

Facebook publie React : l'interface devient une fonction de l'état. Ta stack front actuelle.

2017 · WEBASSEMBLY

Un format binaire que les navigateurs exécutent à côté de JavaScript, pour le calcul lourd (jeux, vidéo). Il complète JavaScript, il ne le remplace pas.

CÔTÉ SYMFONY

Twig fabrique le HTML sur le serveur. Symfony UX (Stimulus, Turbo) ajoute juste assez de JavaScript pour faire vivre ces pages, sans écrire une application React complète.

// InscriptionController.php
#[Route('/inscription', methods: ['POST'])]
public function inscrire(Request $request, EntityManagerInterface $em): Response
{
    $user = new User();
    $user->setEmail($request->request->get('email'));
    $em->persist($user);
    $em->flush();

    return $this->redirectToRoute('merci');
}
VOIR LA RÉPONSE

La seule vérification est dans le navigateur. Une requête envoyée avec curl ou modifiée dans les outils de développement enregistre n'importe quoi en base, même une chaîne vide. Il faut valider côté serveur : des contraintes #[Assert\NotBlank] et #[Assert\Email] sur l'entité, puis $validator->validate($user) (ou un formulaire Symfony) avant le persist. Le JavaScript reste utile, mais seulement pour le confort.

// Page produit : l'API Symfony renvoie {"stock": "0"}
const res = await fetch('/api/produits/12');
const produit = await res.json();

if (produit.stock) {
  boutonAcheter.disabled = false;
}
VOIR LA RÉPONSE

"0" est une chaîne non vide, donc « vraie » : le bouton s'active alors que le stock est vide. Côté front, compare un vrai nombre : Number(produit.stock) > 0. Côté API, corrige la source : sérialise stock en entier, pas en chaîne.

// Afficher le prénom de l'utilisateur connecté
let user;
fetch('/api/me')
  .then((r) => r.json())
  .then((data) => { user = data; });

titre.textContent = `Salut ${user.prenom}`;
VOIR LA RÉPONSE

La dernière ligne s'exécute avant que la réponse arrive : la suite du fetch attend dans une file (section 5). user vaut encore undefined, d'où TypeError: Cannot read properties of undefined (reading 'prenom'). Corrige avec une fonction async : const user = await (await fetch('/api/me')).json(); puis seulement l'affichage.

// React : un bouton qui doit ajouter 2 likes par clic
function Compteur() {
  const [likes, setLikes] = useState(0);

  function doubleLike() {
    setLikes(likes + 1);
    setLikes(likes + 1);
  }

  return <button onClick={doubleLike}>♥ {likes}</button>;
}
VOIR LA RÉPONSE

Les deux appels lisent la même valeur de likes, celle du rendu en cours (disons 0). Ils demandent tous les deux « mets 1 ». Résultat : +1 par clic. Passe une fonction, qui reçoit la valeur la plus récente : setLikes((n) => n + 1), deux fois.
